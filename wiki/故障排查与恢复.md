# 故障排查与恢复

## 先保持只读

排查顺序：

1. 打开 WebUI，记录状态、模式、轨道和快照时间；
2. 点击“刷新状态”，确认探针结果；
3. 点击“一键体检”和“规则审计”；
4. 查看事件日志；
5. 只有在确认健康门控条件后才执行网络动作。

## 页面未打开或无响应

- 确认 KernelSU 管理器自身能打开其他模块 WebUI；
- 重新打开面板，观察顶部是否出现“已发送”；
- 若 90 秒后自动解锁，说明桥接回调丢失，尝试重开面板；
- 不要在无反馈时连续点击同一动作。

## 快照年龄持续增长

```sh
su -c 'cat /data/adb/modules/rmg_netguard/run/guard.pid'
su -c 'pgrep -f rmg_netguard/scripts/guard.sh'
su -c 'tail -n 50 /data/adb/modules/rmg_netguard/run/events.log'
```

若 guard 不存在，可在确认 AGH 未受影响后手动执行 `service.sh`。不要直接 kill
不相关进程。

## `DOWN_PORT`

含义：劫持规则在，但 5591 没有监听，可能出现 DNS 黑洞。

优先检查：

```sh
su -c 'pidof AdGuardHome'
su -c 'grep -i ":15D7 " /proc/net/udp /proc/net/udp6'
su -c 'iptables -w -t nat -S OUTPUT'
```

在 AGH 健康门控未通过时，不要强行恢复 AGH 劫持。必要时通过 AGH 管理模块或
KernelSU 安全模式恢复解析。

## `INCONSISTENT`

含义：AGH 进程存在，但 `OUTPUT -> ADGUARD_REDIRECT_DNS` 不存在。

- 若 DNS 实测正常，可能是 VPN 路径仍在工作；
- 若用户期望轨道 A，需先确认 AGH 5591 健康，再在 WebUI 恢复劫持；
- 不要通过重建整条 AGH 链来“修复”，先核对 AGH 模块自身状态。

## 探针 `BLOCKED / UNKNOWN`

这表示主测试域名被拦截，但第二个测试域名未返回可判定结果。可能原因：

- 两个域名的规则策略不同；
- 缓存或 UDP 超时；
- AGH 对特定域名静默丢包；
- 设备当前 DNS 路径不是预期轨道。

它不能单独证明 AGH 整体退化。先检查 AGH querylog、5591 和实际终端过滤效果，再
决定是否重启 AGH。

## querylog 年龄较大

querylog 年龄只代表文件最近修改时间。设备夜间无 DNS 查询、缓存命中或 querylog
写入策略变化都可能让它增长，不应单独触发重启。

## DNS 集成显示“未打补丁”

- 确认 Clash Meta 正在运行；
- 确认活动 profile UUID 可读；
- 检查 backup 与 profile 是否匹配；
- 订阅更新可能改写 profile，等待 guard 漂移检测或重新开启集成；
- 不要在未备份的情况下手工改 profile。

## 紧急恢复

优先级从高到低：

1. KernelSU 安全模式 / 禁用模块；
2. 停止 AGH 的劫持路径并恢复系统 DNS；
3. 从 `run/backups/` 恢复活动 profile；
4. 按设备恢复说明重启，确认无其他模块冲突。

不要未经确认刷分区、清除模块目录或执行 `iptables -F`。
