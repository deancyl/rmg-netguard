# 开发与验证

## 代码结构

```text
module/
  module.prop
  customize.sh
  service.sh
  uninstall.sh
  scripts/
    env.sh
    guard.sh
    controller.sh
    config_toggle.sh
    probe.sh
    rules_audit.sh
    rescue.sh
    webui.sh
  webroot/index.html
tests/webui/verify.js
build_zip.py
verify_zip.py
```

## 构建

```sh
python build_zip.py
python verify_zip.py
```

`build_zip.py` 会：

- 把 `module/` 内容放到 zip 根目录；
- 排除点文件、`*.bak*` 和 `*~`；
- 校验 zip 无损坏；
- 校验源码无 CRLF 和 BOM；
- 输出 zip 大小、条目和 MD5。

`verify_zip.py` 会逐字节比较 zip 与源码，并检查备份文件是否泄漏。

## WebUI 回归测试

```sh
npm install
npx playwright install chromium
npm run test:webui
```

测试在真实 Chromium 中打开页面，使用 384×823 CSS 视口和 KernelSU 桥接桩，覆盖：

- 首屏只调用 `status_fast`；
- 30 秒自动刷新定时器启动；
- 模式采用 controller 实时值；
- 未执行探针时显示“未检测”；
- 每个动作立即出现反馈；
- 面板内确认与取消；
- 忙碌期间重复调用有提示；
- 非零退出码显示红色失败；
- 页面布局、无阻塞对话框、无 JavaScript 异常。

## shell 检查

模块脚本必须以 Android `sh` / toybox 为运行环境：

- 不使用 bash 专属语法；
- 不假设 `flock -w` 永远存在；
- 不依赖外部 Python / Node；
- 命令失败必须返回非零；
- 临时文件使用 PID 后缀，避免并发冲突；
- 修改 profile 使用临时文件重写，不使用 `sed -i`。

在设备上执行前，至少进行静态语法检查和隔离目录模拟。涉及 `iptables` 或 profile
的测试必须在可恢复环境进行。

## 版本规则

发布时必须保持一致：

- `module/module.prop` 的 `version`
- `versionCode`
- `webroot/index.html` 显示的版本
- `build_zip.py` / `verify_zip.py` 输出文件名
- Git tag，例如 `v2.2.1`
- Release 标题和 changelog

版本不一致会导致 Actions 发布失败。

## 发布流程

1. 更新 `CHANGELOG.md`、README、模块版本和 UI 版本。
2. 本地运行构建、zip 校验和 WebUI 测试。
3. 提交并推送 `main`。
4. 创建并推送 tag：

```sh
git tag -a v2.2.1 -m "RMG NetGuard v2.2.1"
git push origin v2.2.1
```

5. `.github/workflows/release.yml` 构建 zip、生成 SHA-256 并创建 Release。
6. 检查 Release 资产、tag、模块版本和文档链接。

## 提交边界

- 不提交设备序列号、token、订阅地址或未脱敏日志；
- 不提交 `node_modules`、浏览器截图或模块 zip；
- 不回退工作区中与本次任务无关的用户改动；
- 生产设备动作需要单独说明风险和回滚路径。
